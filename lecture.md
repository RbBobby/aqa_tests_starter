# Лекция. Первые API-тесты: продукты, бренды, pytest и слой сервисов

Сегодня разбираем публичный тестовый сайт и пишем к нему первые автотесты. Цель занятия — пройти путь от ручного запроса в клиенте API до структурированного pytest-проекта: виртуальное окружение, маркировки, отладка ответа и вынос HTTP-вызовов в сервисы.

---

## 1. Смотрим API вручную

На тестовом сайте есть раздел API. Там лежит первая ручка, с которой начнём: список продуктов.

Открываем клиент, похожий на Postman. Вставляем URL метода, отправляем **GET**. Ожидаем статус **200** и полный список продуктов.

В теле ответа приходит JSON. В этой конкретной реализации внутри JSON ещё лежит поле вроде `responseCode`. Обычно код ответа смотрят в HTTP-статусе, а не в теле. Здесь это особенность сервиса, не образец хорошего API.

Дальше смотрим полезную нагрузку. Есть массив `products`. Один элемент массива — один продукт. У продукта есть:

- `id`
- имя
- цена
- бренд
- категория (например, Women / Tops или Men / Tshirts)

Категории и признаки различаются от товара к товару.

URL этого метода удобно скопировать в заметку или в тест, чтобы не держать его только в клиенте. Метод называется **GET productsList**.

Рядом указан **POST productsList**. Документация говорит, что метод не поддерживается. Отсюда уже можно собрать тест-кейс: запрос POST на эту ручку должен вернуть **405 Method Not Allowed**.

Есть и поиск продуктов, например по категории. В тело запроса можно передать категорию вроде Tshirts и получить товары этой категории. На этом занятии основной путь — список продуктов и список брендов.

## 2. Правила pytest и каркас теста

Переходим в IDE.

Чтобы pytest увидел файл, имя должно **начинаться или заканчиваться** словом `test`. Удобная схема: `test_get_products.py`.

В начале файла подключаем две библиотеки:

- **pytest** — фреймворк запуска тестов
- **requests** — HTTP-клиент

Позже импорт `requests` уйдёт из тестов в слой сервисов. Тогда в тесте останется один раз описать зависимости проекта, а не копировать низкоуровневый `requests.get` в каждый файл.

Маркировки (`@mark`) группируют тесты. Это не магия: строка `@pytest.mark.api` вешает метку. Дальше можно запускать только нужную группу:

```bash
pytest -m api
```

Так собирают пачки для CI: API-тесты отдельно, UI отдельно, smoke отдельно. На собеседованиях часто спрашивают, как группировать тесты — маркировки как раз про это.

После меток создаём **класс** или функцию. Класс объединяет тесты одной области. Для продуктов логично что-то вроде `TestGetProducts`: внутри только сценарии микросервиса продуктов.

Метод теста внутри класса всегда принимает `self`.

## 3. Виртуальное окружение и зависимости

Библиотеки могут подтягиваться из системного Python на машине. Это плохо для командной работы: версии расходятся, «у меня locally стоит одно, у коллеги другое».

Поэтому создаём **virtual environment** — изолированное окружение только для этого проекта.

```bash
python3 -m venv .venv
```

Точка в `.venv` — это имя папки, не особый синтаксис команды. После создания папки внутри появляется скрипт активации. На macOS / Linux:

```bash
source .venv/bin/activate
```

Эти команды стоит сразу положить в README, чтобы человек, склонировавший репозиторий, понял, как поднять проект.

Зависимости фиксируем в `requirements.txt`:

```
pytest
requests
```

Установка внутри активированного окружения:

```bash
pip install -r requirements.txt
```

Если после установки IDE всё ещё подчёркивает импорты, выбран не тот интерпретатор. Command Palette → **Python: Select Interpreter** → интерпретатор из `.venv`. После этого подсветка пропадает.

Идея: каждый, кто работает с фреймворком, ставит одни и те же пакеты в своё локальное окружение проекта, а не опирается на случайный набор библиотек на компьютере.

## 4. Первый тест: статус-код списка продуктов

Базовый URL и endpoint лучше разделить:

- `BASE_URL` — общая часть, куда ходят все запросы проекта
- `ENDPOINT` — конкретный путь, например `/productsList`
- итоговый URL — конкатенация строк

Так сразу видно, **куда** ходим и **каким методом**. Всё можно было зашить в одну строку, но тогда сложнее читать тесты.

Первая проверка — только статус:

1. Собрать URL.
2. Вызвать `requests.get(url)`.
3. Сохранить ответ в `response`.
4. Проверить: `assert response.status_code == 200`.

Все проверки в pytest идут через `assert`.

Метод `get` принимает URL и набор необязательных аргументов (query, headers и т.д.). Если их не передавать, используются значения по умолчанию. Для простого GET списка продуктов достаточно URL.

Заглянуть в сигнатуру можно через Go to Definition. Менять код библиотеки в site-packages не нужно: только читать комментарии.

Тест можно запустить кнопкой рядом с функцией. Если зелёный — статус 200 пришёл. Дальше полезно понять, **что именно** лежит в `response`.

## 5. Отладка ответа

В VS Code / Cursor создаём конфигурацию запуска. Для pytest это не «Python: Current File», а модуль `pytest`.

Пример `launch.json`:

- `module`: `pytest`
- аргументы: `-v` (подробный вывод) и `${file}` (текущий открытый файл)

Ставим breakpoint на строке, где создаётся `response`, запускаем debugger, открываем Debug Console.

Что обычно важно для тестов:

- `status_code` — HTTP-статус (отдельно от тела)
- `reason` — краткая расшифровка, например OK
- `text` — сырое тело
- `.json()` — разбор тела в словарь Python
- `url` — куда ушёл запрос
- внутри `response.request` — метод, путь, полный URL отправленного запроса

Служебные заголовки и служебные поля в теле для большинства проверок не нужны. Поле `responseCode` внутри JSON здесь лишнее с точки зрения контракта: код уже есть в HTTP-статусе.

`text` — сырая строка. Пока её не прогнали через `.json()`, это не провалидированный объект. В Debug Console сырой текст в словарь не всегда удобно смотреть; для работы с ключами используем `.json()`.

## 6. Второй тест: количество продуктов

В том же классе добавляем тест на количество товаров.

Снова GET на ту же ручку. Дальше:

```python
data_json = response.json()
count_of_products = len(data_json["products"])
assert count_of_products > 33
```

`len` считает элементы контейнера. К ключу JSON обращаемся квадратными скобками: `data_json["products"]`.

Промежуточная переменная `data_json` не обязательна: ту же конструкцию можно вставить прямо в `len(...)`. Отдельная переменная читаемее.

Почему в тесте статуса не нужен `.json()`? Потому что `status_code` уже есть у объекта ответа. А массив продуктов лежит внутри тела, его сначала нужно разобрать.

Числа в каталоге могут идти с пропусками id: 34 нет, 32 нет. Значит, нельзя считать количество по максимальному id. Считаем длину массива.

Если порог завышен (например, `> 40`, а товаров 34), тест падает. Сообщение pytest подсветит фактическое значение и ожидаемое. Порог нужно выбирать из реального контракта: «на сайте должно быть больше N продуктов, иначе ассортимент недостаточный».

Иногда падает и тест на 200: сервер вернул **503**. Это не баг теста, а сбой сервиса. Нормальная реакция: завести тикет, при необходимости посмотреть логи, перезапустить тест. 503 может исчезнуть на ретесте — типичная нестабильность внешнего стенда.

## 7. Маркировки на практике

На класс или на отдельные тесты вешаем несколько меток, например:

- `api`
- `smoke`
- `products` или `brands`

Запуск без фильтра соберёт все тесты. Запуск `pytest -m api` оставит только API. Запуск `pytest -m brands` — только бренды.

Pytest напишет, сколько собрано, сколько выбрано, сколько пропущено. Пропущены тесты без запрошенной метки.

Маркировок может быть сколько угодно. `api` и `smoke` специально разные: в smoke могут входить и UI-тесты. Одна метка на всё смешает пачки.

Это удобно для CI: разные job запускают разные `-m`.

## 8. Второй файл: бренды

Логику режем по файлам:

- `test_get_products.py` — продукты
- `test_get_brands.py` — бренды

Не смешиваем ручку `brandsList` с продуктами. При следующем заходе в проект сразу ясно, какой файл за что отвечает.

**GET brandsList** возвращает список брендов. У элемента обычно только `id` и `brand`. Дополнительных полей нет.

На сайте часть методов (PUT, иногда POST) помечена как неподдерживаемые. Для учебного стенда часто оставляют безопасные методы, чтобы случайно не перегрузить реализацию.

В ответе снова может быть лишний `responseCode` в теле. Смотрим массив `brands`: начало и конец списка видны в JSON.

Замечание по данным: бренды могут повторяться. С точки зрения домена бренд обычно уникален. Повтор — повод задать вопрос к реализации, не обязательно сразу падать тестом, пока нет согласованного требования.

Тесты брендов по структуре те же: статус 200 и `len(data_json["brands"]) > 10` (порог — по факту каталога). Метки: `api`, `smoke`, `brands`. Тогда:

- `pytest -m api` — продукты и бренды
- `pytest -m brands` — только бренды
- `pytest -m products` — только продукты

## 9. Слой services: зачем убирать HTTP из теста

Когда файлов больше, в каждом тесте повторяются `BASE_URL`, endpoint и `requests.get`. Если смотреть только на тест, не всегда понятно, *какой* это запрос: виден технический URL, а не действие «получить бренды».

Выносим вызовы в пакет `services`:

- `services/__init__.py` — пустой файл, чтобы папка была пакетом Python
- `services/brands_service.py`
- `services/products_service.py`

Класс сервиса хранит `base_url` и даёт понятные методы, например `get_brands()`. Внутри по-прежнему `requests.get`, но тест читается так:

```text
ответ = сервис.get_brands()
проверить статус
```

Из теста импорт `requests` убираем. Импортируем сервис. Создаём объект класса и вызываем метод.

Конструктор в Python — `__init__` (два подчёркивания слева и справа). В нём сохраняем `self.base_url`. Глобальные константы принято писать заглавными буквами.

Сервис должен возвращать объект ответа `requests`, а не сразу `.json()`. Иначе в тесте нельзя проверить `status_code` и повторно вызвать `.json()`.

Сервис не импортирует константы из тестовых файлов: зависимости идут от тестов к сервисам, не наоборот.

Дальше по той же схеме делают `ProductsService` с методом вроде `get_products()` и переводят тесты продуктов на сервис. Названия методов разные, идея одна: тест описывает *что* проверяем, сервис — *как* ходим в API.

Позже в тот же класс можно добавить POST и другие методы той же ручки. Тесты не раздуваются копипастой URL.

4. Группировать тесты маркировками `api` / `smoke` / `products` / `brands`.
5. Отлаживать `response` через launch-конфиг pytest.

## Домашнее задание

Повторить для продуктов то, что на занятии сделали для брендов.

### Что сделать

1. Заполнить `services/products_service.py`.
2. Поправить `test_get_products.py`, чтобы тесты ходили в API через сервис, а не через `requests.get` напрямую.

Образец — `services/brands_service.py` и `test_get_brands.py`. Логика та же, названия и endpoint другие.

### Сервис

В `ProductsService`:

- конструктор `__init__` (два подчёркивания с каждой стороны) сохраняет `base_url`;
- метод `get_products()` собирает URL `base_url + "/productsList"` и делает GET;
- метод **возвращает объект ответа** `requests` (`return response` или сразу `return requests.get(url)`), а не `response.json()`;
- `BASE_URL` живёт в сервисе (или в общем месте проекта), **не импортируется из тестового файла**.

Файл сейчас пустой — его нужно написать целиком.

### Тесты

В `test_get_products.py`:

- убрать `import requests`, `BASE_URL`, `ENDPOINT`, `URL`;
- импортировать `ProductsService`;
- в каждом тесте создать объект сервиса и вызывать `get_products()`;
- проверки оставить те же: статус `200` и `len(data_json["products"]) > 33`.

Маркировки `api`, `smoke`, `products` не трогать.

### Как проверить, что ДЗ готово

```bash
source .venv/bin/activate
pytest -v -m products
```

Оба теста продуктов должны пройти. `requests` в файле тестов продуктов больше не используется.

### На что не наступить

- `_init__` вместо `__init__` — конструктор не вызовется, будет ошибка на `self.base_url`.
- `return response.json()` — в тесте не будет `status_code`.
- импорт URL из `test_get_*.py` в сервис — зависимость перевёрнута.
